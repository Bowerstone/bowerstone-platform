## 2026-10-13: The migration runner (Platform Build Plan, task 1.2)
- Status: Ready for review
- What and why: Applies each module's numbered SQL files exactly once and in order, records them in `core.applied_migration` with a checksum, and undoes them with their down files. It replaces Alembic, which would need one migration branch per app.
  - `migration_files.py` reads a module's `migrations` folder and refuses:
    - badly named, unexpected, repeated, or missing files, and gaps in the numbering
    - an upgrade file without a down file
    - empty files, invalid UTF-8, a byte-order mark, and Windows line endings
  - `migrate.py`:
    - `upgrade` and `downgrade` run on one connection that holds a session-level advisory lock for the whole run.
    - A run refuses when the database and the files disagree: a file changed or renamed after it was applied, a gap in the records, or a database ahead of the code.
    - Each file runs in one transaction with its record. A file marked `-- bowerstone: no-transaction` runs alone, outside a transaction, and PostgreSQL refuses a second statement in it.
  - Choices agreed with Ilia:
    - a separate migration time limit, `BOWERSTONE_MIGRATION_STATEMENT_TIMEOUT_MS`, defaulting to 30 minutes
    - every migration must have a down file
    - a second run waits for the lock, up to that time limit
  - Departure from the plan's layout: instead of one `migrate.py`, the runner is a package, `bowerstone_engine.migrations` (Ilia moved the files there), of four modules, so each stays under 300 lines with one job (CLAUDE.md rule 8):
    - `migration_files.py` reads and checks the files
    - `migration_execution.py` runs them and holds the lock
    - `migration_records.py` keeps `core.applied_migration`
    - `migrate.py` holds `upgrade` and `downgrade`
  - The runner does not run the database check itself. Task 1.4's `upgrade_all` runs it first, as the plan says.
- Files:
  - Engine:
    - New package `engine/src/bowerstone_engine/migrations/`: `__init__.py`, `migrate.py`, `migration_execution.py`, `migration_files.py`, `migration_records.py`
    - Changed: `config.py` (`migration_statement_timeout_ms` and `MigrationSettings.migration_limits`), `errors.py` (`MigrationError`)
  - Tests: `engine/tests/test_migration_files.py`, `engine/tests/test_migration_settings.py`, and `engine/tests/migration_runner/` (`conftest.py`, `test_upgrade.py`, `test_downgrade.py`, `test_lock_and_no_transaction.py`)
  - This file.
- Tests: 94 new tests, run with `make test`. Each runner test gets a PostgreSQL 18 database of its own, because migrations commit.
  - The plan's "done when" list:
    - a fresh upgrade
    - a second run that changes nothing
    - an edited file, refused even when the edit is a comment
    - a gap in numbering
    - a downgrade
    - two runs at the same time, which apply each migration once
    - a no-transaction file that creates and drops an index with `CONCURRENTLY`, leaving it valid
    - a no-transaction file with two statements, refused with nothing run or recorded
  - Also covered:
    - **Badly named files:** ten forms of bad name, a subfolder, number 0000, repeated numbers, and numbers not starting at 0001
    - **Partner files:** an upgrade file with no down file, a down file with no upgrade file, and a down file with a mismatched name
    - **File contents:** Windows line endings, a lone carriage return, a byte-order mark, invalid UTF-8, and empty or white-space files, each checked in both the upgrade and the down file. Unicode text is accepted, with its checksum taken over the bytes.
    - **The no-transaction marker:** only an exact first line counts
    - **Module names:** valid and invalid
    - **Database out of step with the files:** a renamed file, a database ahead of the code, a gap in the records, and a slice of the migrations passed in
    - **Failures:** a failing file rolls back with its record while earlier files stay; a failing down file keeps its record; normal transactions resume after a no-transaction file
    - **`%` signs:** a PL/pgSQL `RAISE` with `%` and `%%` gives exactly the right message
    - **Records:** kept apart per module; the record table is created once, owned by `bowerstone_owner`, and refuses a version out of range or a malformed checksum
    - **Connections and the lock:** a connection inside a transaction is refused; a run waiting too long for the lock gives up with a clear message; the lock is released after a failed run
    - **Downgrade targets:** 0, the current version and above, and refused targets (-1, past the end, `True`); upgrading again after a downgrade
    - **The migration time limit:** its default, bounds, refused values, and the limits it gives a migration run
- Scaling and security:
  - **One run at a time:** a session-level advisory lock on the run's single connection. A second run waits, up to the migration time limit, and is then refused with a clear message. The lock is released when the run ends or fails.
  - **Edits and stale code are refused:** a file changed or renamed after it was applied, and a database ahead of the code. Line-ending problems fail as such, not as a changed checksum.
  - **Failures leave nothing behind:** each file runs in one transaction with its record. A no-transaction file is the exception: PostgreSQL refuses a second statement in it, and its record is written only after it succeeds. If it succeeds but the record write then fails, the next run retries the statement and fails loudly. A failed `CREATE INDEX CONCURRENTLY` can also leave an invalid index. Both points belong in the migration-writing guidance for task 3.2.
  - **Migration files run as written,** through the driver with no parameters. They come from Bowerstone's own packages, never from users. Records are written with bound parameters.
  - **Time limit:** migration statements get 30 minutes by default; the API keeps its 10-second limit.
- Dependencies added: None

## 2026-10-13: Checks on GitHub Actions (part of Platform Build Plan, task 6.3, brought forward)
- Status: Ready for review
- What and why: Every push and every pull request runs `make lint`, `make test`, and `make security` on GitHub Actions, in the same pinned containers used on the development computer. A change that breaks a test, a lint rule, or a security check shows as a failed run before it is merged. Ilia asked for this ahead of task 6.3, which still adds the end-to-end test and the remaining jobs.
- Files: `.github/workflows/checks.yml` (new); `README.md` (a new "Automated checks" section); this file.
- Tests:
  - The workflow file was parsed as YAML.
  - Its steps were rehearsed locally from a clean start: a separate Compose project with new volumes and a new database, throwaway passwords made the way the workflow makes them, and Make running through `sh` as on Linux. `make lint test security` passed in 47 seconds, with 228 tests passing. The rehearsal's containers, volumes, and passwords file were removed afterwards.
  - The first real run happens on GitHub, when this change is pushed.
- Scaling and security:
  - **Read-only:** the job's token may only read the repository.
  - **No token left behind:** the checkout leaves no access token in the repository, which the containers mount.
  - **Pinned action:** `actions/checkout` is pinned to its v7.0.1 commit, so a moved tag cannot change what runs.
  - **No stored secrets:** each run makes its own throwaway database passwords, hides them in the log, and stores them nowhere, so the workflow needs no GitHub secrets.
  - **Bounded runs:** a 20-minute limit, and a newer push to the same branch cancels the older run.
  - **Root-owned files:** the containers run as root, so files they write in the workspace belong to root. That is harmless on GitHub's runners, which are discarded after each job, but task 6.3 must settle it before any self-hosted runner is used.
  - **gitleaks** scans the whole history on every run. The staged-changes scan finds nothing in CI, because nothing is staged there.
- Dependencies added: `actions/checkout` v7.0.1 (MIT), a GitHub Action used only by the workflow, never shipped.

## 2026-10-13: Settings, connections, and the database check (Platform Build Plan, task 1.1)
- Status: Ready for review
- What and why: Gives the engine its settings, a database connection pool with fixed limits, a way to record which user makes a change, and a check that refuses to run against the wrong database.
  - `config.py`: `ApiSettings` and `MigrationSettings` are read from `BOWERSTONE_` variables. The API's settings never include the owner role's database address, so the running API never holds the owner's password.
  - `db.py`: `create_connection_pool` makes a fixed-size pool whose connections each start with a statement timeout, a connect timeout, and the UTC time zone. `set_current_user` records the user for the change history until the transaction ends.
  - `database_check.py`: `check_database` refuses unless the server is PostgreSQL 18, the database uses the built-in `C.UTF-8` locale, both Bowerstone roles exist and neither is a superuser, and the current user is `bowerstone_owner`.
  - Choices agreed with Ilia: synchronous database access; default values for the connection limits only; `static_dir` and `max_body_bytes` arrive in task 1.5, which first uses them.
  - Required of task 1.5: never show or log a database error message as it is. SQLAlchemy leaves bound values out of its error text, but PostgreSQL's own message can quote a value, such as text that failed to read as a number, or the key in a unique-constraint error. `test_postgresql_messages_can_still_quote_a_value` records this.
  - Additions to the plan:
    - The database check also refuses either role being a superuser.
    - Each settings model checks that its database address signs in as its own role.
    - Every connection uses the UTC time zone.
    - The check lives in `database_check.py` rather than `migrate.py`, so each file keeps one job (CLAUDE.md rule 8).
- Files:
  - Engine: `engine/src/bowerstone_engine/config.py`, `db.py`, `database_check.py`, `errors.py`
  - Tests: `engine/tests/conftest.py`, `test_config.py`, `test_connection_pool.py`, `test_database_check.py`, `test_set_current_user.py`
  - Tooling:
    - `compose.dev.yaml`: the engine container gets its database addresses and waits for a healthy database
    - `Makefile`: `lint` and `security` no longer start the database
    - `pyproject.toml` and `uv.lock`: the new dependencies; mypy, pytest, and ruff cover `engine/tests`; the pydantic mypy plugin
    - `.env.example`: passwords must be letters and digits
  - This file.
- Tests: 99 new tests, run with `make test` against a fresh PostgreSQL 18 database that each run creates and drops.
  - `test_config.py`, 46 tests:
    - settings read from the environment
    - each required value missing
    - unknown environments, including different capitalisation and a leading space
    - wrong drivers, wrong roles, missing host or database, unreadable addresses, and an empty address, with the password never in the message
    - the API's settings never reading the owner's address, and passwords hidden when settings are printed
    - every limit's defaults and bounds, and refused values: zero, negative, too large, fractional, text, empty, 1,000 digits, and Arabic-Indic digits
    - settings that cannot be changed once read
  - `test_database_check.py`, 28 tests:
    - the logic on made-up facts: PostgreSQL 10, 17, 18.0, 18.9999, and 19; the operating system's, ICU, built-in `C`, and `PG_UNICODE_FAST` locales; each role missing, both missing, each a superuser; three wrong users; every problem at once
    - against PostgreSQL 18: passes as the owner; refuses the app role; refuses a database made with the operating system's locale
    - refuses each missing role and a superuser role. The tests rename or change a role inside a transaction that is rolled back, and check that the role is back afterwards.
  - `test_connection_pool.py`, 8 tests:
    - every pooled connection has the statement timeout and the UTC time zone
    - a 100 ms timeout stops a 1 s query, and a short query still finishes
    - a pool of 2 never opens a third connection (counted on the server); the third request fails after the 1 s pool timeout
    - a queued request gets the next free connection
    - a server that accepts but never answers is given up on after the 2 s connect timeout
    - SQLAlchemy keeps bound values out of its error text, and PostgreSQL's own message can still quote one
  - `test_set_current_user.py`, 17 tests:
    - the user is recorded for the transaction; `None` records nothing; the largest bigint is accepted
    - the user is forgotten after commit and after rollback, and is not passed to the next request on the same pooled connection
    - two concurrent transactions each see only their own user
    - refused outside a transaction
    - refused IDs: 0, -1, `True`, `False`, the largest bigint plus one, 1.5, `"5"`, `""`, and `b"5"`
- Scaling and security:
  - **The API never holds the owner's password.** `ApiSettings` cannot read the owner's address, and each settings model refuses an address that signs in as any other role.
  - **Fixed pool.** It never opens more than its size, and a request waits at most the pool timeout. Every connection has a statement timeout and a connect timeout, so no query or connection attempt waits forever.
  - **No user leaks between requests.** The recorded user lasts only until the transaction ends.
  - **Secrets stay out of messages.** Database addresses are kept as secrets and never appear in printed settings or error messages. SQLAlchemy leaves bound values out of its errors and logs; task 1.5 must handle PostgreSQL's own messages, as above.
  - **SQL:** queries use bound parameters. Database and role names in test setup are quoted by psycopg's `sql` module, because names cannot be bound parameters.
  - **Development only:** the engine container holds the admin, owner, and app passwords. The release image (task 6.1) separates them.
  - **Leftover test databases:** a test run killed partway can leave a `bowerstone_test_*` database behind. Normal runs drop theirs.

  - psycopg[binary] 3.3.6 (LGPL-3.0-only); psycopg-binary bundles libpq

  - `uv.lock` now pins 58 packages.

## 2026-10-12: Platform tooling (Platform Build Plan, task 0.2)
- Status: Ready for review
- What and why: Sets up the development tooling, so a computer with only Git, Make, and Docker Desktop can work on the platform. Postgres 18, Python 3.13 with `uv`, and Node 22 run in containers defined in `compose.dev.yaml`, and every `make` target runs through them.
  - `make db` starts Postgres 18.6 with the built-in `C.UTF-8` locale and the roles `bowerstone_owner` and `bowerstone_app`. It waits for a health check that confirms all three.
  - `make lint` runs `ruff check`, `ruff format --check`, mypy in strict mode, the 300-line file check, and the TypeScript check.
  - `make test` runs the tests, including the guard hook's tests in `.claude/hooks/`.
  - `make security` runs bandit, pip-audit, npm audit, and gitleaks. CLAUDE.md rule 7 runs them on every change, so they start here rather than in task 6.3.
  - `make migrate` and `make dev` stop with "Not yet set up" and status 2, until tasks 1.6 and 2.2.
  - Departures from the plan, agreed with Ilia: TypeScript is installed now, so `web/ui/src/index.ts` exists as the design system's empty entry module, giving the check a file to check. The 300-line check covers code, SQL, and shell scripts.
  - Additions not in the plan: `ruff format --check` in `make lint`, and both workspaces marked `"private": true` so npm cannot publish them before task 3.1.
  - Licence: `AGPL-3.0-only`, Ilia's decision on 2026-10-12. It is set in `pyproject.toml`, all three `package.json` files, and the README.
- Files:
  - Containers and database: `compose.dev.yaml`, `.env.example`, `docker/initdb/01-roles.sh` (the Initial Setup Plan's script, made executable), `docker/check_database.sh`
  - Python: `pyproject.toml`, `uv.lock`, `engine/src/bowerstone_engine/__init__.py`, `scripts/check_file_length.py`

- Scaling and security:
  - **Passwords** come only from the git-ignored `.env`. Compose stops with a message naming any missing or empty one, rather than starting with an empty password. Every target needs `.env`, because Compose reads the whole file.
  - **No database port is published.** Only containers on the Compose network can reach Postgres, and they must use a password (`scram-sha-256`).
  - **Trust inside the database container:** the Postgres image trusts connections from inside its own container (the local socket and `127.0.0.1`). That is the image's default and is left unchanged. Anyone who can open a shell in the container already controls Docker. Task 6.1 can tighten it for the release image.
  - **Pinned images:** every image is pinned by version and digest, so a changed upstream image cannot slip in. Updating one is a manual change for now.
  - **No Git in the development images.** Nothing run in the `engine` or `web` containers can write the repository's history. A test checks `engine`; `web` was checked by hand. gitleaks runs with the repository mounted read-only.
  - **Ruff skips Markdown,** so it never reformats the code examples in `docs/decisions/`.
  - **Python:** `uv` never downloads a Python other than the image's 3.13, and `--locked` fails if `uv.lock` is out of date.
  - **Containers run as root.** That is harmless on Docker Desktop, but on Linux, files they write into the repository would belong to root. Task 6.3, the first to run on Linux, settles the container user.
  - **Speed on Windows:** packages live in named volumes, off the slow Windows mount.
